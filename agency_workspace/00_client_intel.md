## API Integration Intelligence

### 8.1 — How to Start a Conversation with Antigravity

**Finding:** Antigravity IDE does NOT expose a native LLM API endpoint for third-party extensions to call directly. There is no `/v1/devio/invoke` or equivalent. The V1 assumption (`http://localhost:11434/v1/devio/invoke`) was **incorrect** — this endpoint does not exist.

The correct integration mechanism is the **Antigravity Link extension** (community, MIT licensed), which acts as a local HTTP bridge to the active IDE session. It exposes the API at `https://localhost:3000` (default port, configurable).

**Verified endpoint for sending a prompt:**

```
POST https://localhost:3000/send
Authorization: Bearer <token>
Content-Type: application/json

{
  "message": "your prompt text here"
}
```

**Response (200 OK):**
```json
{
  "success": true,
  "method": "vscode_command | cdp_dom",
  "target": "..."
}
```

The `/send` endpoint injects the message text into the active Antigravity chat input and submits it — exactly as if the user typed and pressed Enter. It uses the VS Code command API first, with a CDP DOM injection fallback.

Source: [`openapi.yaml`](https://raw.githubusercontent.com/cafeTechne/antigravity-link-extension/main/openapi.yaml), `/send` path definition.

**Important prerequisite:** Antigravity IDE must be launched with `--remote-debugging-port=9000` (or any port) for the bridge to discover and connect to the session. The Antigravity Link extension must also be installed and its server started.

### 8.2 — How Credentials Are Exposed to Extensions

**Finding:** There is no VS Code extension API export (`getExtension('antigravity').exports`) that returns API credentials. Antigravity does not inject credentials into the extension host environment.

The **bearer token** used to authenticate calls to the Antigravity Link API is:
- Generated by the Antigravity Link extension on first server start.
- Stored in the extension's installation directory (`server.json` or equivalent).
- Printed in the QR code URL as `?token=<value>`.

**How the Devio plugin must obtain the token at runtime:**

Two viable approaches (Architect must choose one):

| Option | Mechanism | Notes |
|:---|:---|:---|
| **A — Read from disk** | Read `server.json` from the known Antigravity Link extension install path | Path: `~/.antigravity-ide/extensions/cafetechne.antigravity-link-extension-*/server.json`. Brittle if extension version changes. |
| **B — User setting** | Expose `devio.antigravityLinkToken` as a SecretStorage entry. User pastes token once from the QR URL. | Clean, reliable. One-time setup. Does NOT require the user to know the endpoint — only the token. |

**Recommended:** Option B. The endpoint (`https://localhost:3000`) is fixed/default and can be a setting. The token is secret and goes in SecretStorage. The user sets it once. This satisfies the brief's constraint that the user does not configure the LLM API key — the Antigravity Link token is different in nature.

Source: [README — For agent builders](https://github.com/cafeTechne/antigravity-link-extension#for-agent-builders), MCP config example, `server.json` reference.

### 8.3 — Response Format and How to Know Generation Is Finished

**Finding:** The `/send` endpoint responds immediately (sync) with `{ "success": true }`. It does NOT wait for the AI to finish generating. This is fire-and-forget.

**To know when generation is complete**, the engine must poll:

```
GET https://localhost:3000/snapshot
Authorization: Bearer <token>
```

**Response (200 OK):**
```json
{
  "html": "<cleaned outerHTML of chat surface>",
  "controlsHtml": "<full body HTML>",
  "controlsMeta": {
    "isGenerating": false,
    "model": { "text": "...", "selector": "..." },
    "mode": { "text": "...", "selector": "..." }
  },
  "isGenerating": false,
  "css": "...",
  "colorScheme": "dark"
}
```

**`isGenerating: false`** = generation complete. The engine polls `/snapshot` on an interval (e.g. every 2 seconds) until `isGenerating` is `false`, then reads the `html` field to extract the agent's response.

**Structured output / tool calls:** Not available via this bridge. The agent's response is free-form text inside the `html` field. The orchestration engine must parse the HTML to extract the agent's text output. The Architect must design a parsing strategy (e.g. target a known CSS selector for the last assistant message).

Source: [`openapi.yaml`](https://raw.githubusercontent.com/cafeTechne/antigravity-link-extension/main/openapi.yaml), `/snapshot` path + `ControlMeta` schema + `isGenerating` field.

### 8.4 — Antigravity MCP: Available Tools

**Finding:** Antigravity Link ships an MCP server (`mcp-server.mjs`) with 9 tools:

| Tool | Description |
|:---|:---|
| `get_snapshot` | Returns current chat surface HTML + generation state |
| `send_message` | Sends a prompt to the active chat |
| `stop_generation` | Cancels active AI generation |
| `get_instances` | Lists active Antigravity windows |
| `switch_instance` | Switches the active CDP target |
| `click_element` | Clicks a DOM element by selector/text/coordinates |
| `get_task` | Reads `task.md.resolved` from brain directory |
| `get_walkthrough` | Reads `walkthrough.md.resolved` |
| `get_plan` | Reads the current implementation plan |

**Can the plugin use MCP tools directly?** Yes, but it requires running the MCP server as a subprocess (`node mcp-server.mjs`) with environment variables `AG_BRIDGE_URL` and `AG_BRIDGE_TOKEN`. This is more complex than direct HTTP calls. **Recommendation:** the plugin should use the HTTP API directly, not MCP. MCP is for AI agents — the plugin IS the orchestrator.

Source: [README — MCP server](https://github.com/cafeTechne/antigravity-link-extension#mcp-server), MCP config example.

## Architectural Implications (for Architect's attention)

1. **The orchestration loop** must use Antigravity Link as the bridge — not a direct LLM API call. There is no direct LLM API for extensions to call.

2. **The conversation flow** is: `POST /send` → poll `GET /snapshot` until `isGenerating: false` → parse HTML response → apply to workspace → advance phase → repeat.

3. **No structured output**. The agent's response is raw HTML. The Architect must design a parsing strategy to extract agent actions from the chat text.

4. **Prerequisite dependency**: the Antigravity Link extension must be installed and running. The Devio plugin must check for this on startup and surface a clear error if it is not available.

5. **Token acquisition**: recommend Option B (user pastes token into SecretStorage once). The `devio.antigravityLinkPort` setting (default: 3000) covers the endpoint.

6. **The model is already selected in Antigravity IDE itself**. The `devio.antigravityModel` setting would need to drive a UI interaction (e.g. `POST /click` on the model selector) — this is fragile. Alternatively, the model selector in the UI is left to the user and `devio.antigravityModel` is dropped or made advisory only. Architect to decide.

## Research Gaps

- The exact CSS selector for extracting the last assistant response from the `/snapshot` HTML is unknown without inspecting a live Antigravity session DOM. The Architect should flag this as a risk and design the parser to be configurable.

## Addendum — Conversation Lifecycle Research

**Research question:** Can the engine create a fresh conversation for each agent turn, instead of accumulating all turns in a single chat?

**Finding: YES — two viable mechanisms confirmed.**

### Mechanism A — VS Code Command (Preferred)

Antigravity IDE, being VS Code-based, exposes the standard command:

```
workbench.action.chat.newChat
```

The Antigravity Link extension already uses the VS Code command API as its primary injection method (before falling back to CDP DOM injection). The engine can invoke this command via the `/click` endpoint targeting the VS Code command palette, OR — more reliably — via a dedicated new endpoint approach.

**However**, the cleaner path is that Antigravity Link's `POST /click` endpoint accepts a `text` parameter to match visible button text. The "New Chat" button exists in the Antigravity IDE UI. This can be triggered as:

```
POST https://localhost:3000/click
Authorization: Bearer <token>
Content-Type: application/json

{ "text": "New Chat" }
```

Source: `openapi.yaml` `/click` definition; CHANGELOG v1.0.20 confirmation that VS Code command API is the primary injection method.

### Mechanism B — `POST /click` with selector

The CHANGELOG (v1.0.20) confirms the extension uses `antigravity.agentSidePanelInputBox` as a known selector. The new chat button has a stable `data-tooltip-id` attribute pattern (similar to the confirmed stop button selector `input-send-button-cancel-tooltip`). The exact selector for "New Chat" is **unconfirmed without live DOM inspection** — flagged as a research gap requiring live validation.

### Recommended implementation approach

For the orchestration engine, the **recommended strategy** is:

1. **Per-phase fresh conversation**: before sending each agent's prompt, trigger `POST /click { "text": "New Chat" }` to open a clean conversation.
2. **Wait for confirmation**: poll `GET /snapshot` until the chat surface is empty (no `html` content from prior turns) before sending the new prompt.
3. **Fallback**: if the click fails (button text changed), log a warning and continue in the existing conversation — degraded quality, not a crash.

This gives each agent a clean context window, preventing cross-contamination between the Researcher's findings, the CEO's proposal, and the Developer's code output.

### Architectural implication for Proposal

The proposal must include:
- `ConversationManager` component responsible for opening a fresh chat before each agent turn
- A configurable setting `devio.freshConversationPerTurn` (boolean, default: `true`) allowing the user to disable this if they prefer a continuous conversation
- The health check must verify that the "New Chat" click mechanism works during onboarding

## Option B Research Addendum — Integrating `devio-antigravity-link-extension`
*Triggered by client request, Phase RESEARCH*

**Finding:** The provided fork (`devio-antigravity-link-extension/`) contains a robust, production-ready implementation of Antigravity Link capabilities that can be directly merged into the Devio extension.

### Key Capabilities Identified
1. **Window Management:** The codebase uses the Chrome DevTools Protocol (CDP) (`src/services/cdp.ts`) to discover all running Antigravity IDE instances (requiring `--remote-debugging-port`). It scores targets to correctly identify chat surfaces and manages switching between multiple windows natively.
2. **MCP Server:** `mcp-server.mjs` is a standalone JSON-RPC server over stdio that exposes 9 tools (`get_snapshot`, `send_message`, `stop_generation`, `get_instances`, `switch_instance`, `click_element`, `get_task`, `get_walkthrough`, `get_plan`). It wraps the local HTTP API.
3. **HTTP API:** An Express server (`src/server/index.ts`) that exposes the CDP interactions as REST endpoints. It handles snapshot hashing and tracking generation state (`isGeneratingTracker.ts`).

### Integration Path (How to Merge)
Instead of relying on brittle HTTP polling to a separate extension, Devio can merge the `src/services/` and `src/server/` directories directly into its own `agency_workspace/src/`. 

- **Direct Internal Integration:** By merging the code, the Devio Orchestrator Engine no longer needs to use `fetch` to `https://localhost:3000`. It can directly call the underlying TypeScript methods (e.g., `captureSnapshot()`, `injectMessage()`, `connectCDP()`).
- **Elimination of Auth/Port Overhead:** Merging removes the need for SecretStorage token management and port configuration, as the Devio extension host process will securely manage the CDP connections in memory.
- **MCP Server Hosting:** Devio can bundle `mcp-server.mjs` to expose its capabilities natively to other AI agents.
- **Recommendation for Architect:** Abandon the HTTP `AgLinkClient` design from the previous proposal. Design the new architecture to directly utilize the CDP services module to drive the orchestration loop, gaining stability and window management features natively.

## Addendum — Global Packaging of Agents & Skills
*Triggered by client request, Phase DELIVERY (redirected to RESEARCH)*

**Finding:** To make agents and skills globally available across any workspace without relying on the original Devio project source, the extension must package these files and install them to the extension's global storage directory provided by the VSCode/Antigravity API.

### Key Implementation Details
1. **Packaging:** The `agents` and `skills` directories must be included in the `.vsix` bundle. Ensure `.vscodeignore` does not exclude them.
2. **Global Storage Installation:** Upon extension activation, the extension should verify if the agency files exist in the globally accessible `context.globalStorageUri`. If not, it must copy them natively from its own installation directory (`context.extensionUri`) to the global storage directory using `vscode.workspace.fs.copy` or Node.js `fs.cpSync`.
3. **Workspace Orchestration:** The engine (`WorkspaceManager` or orchestrator) must then read and write all agency state, agent profiles, and skills from this global path rather than resolving them relative to the current active workspace.
4. Recommendation for Architect: Add an initialization sequence to the `ExtensionContext` activation to handle the global installation. Update all path resolution logic to default to the global storage URI. Specifically:
   - `src/extension.ts`: Pass `context.globalStorageUri.fsPath` down to `PromptBuilder`. Implement the copy logic here.
   - `src/prompt-builder.ts`: Update the `Context: @.agent/skills/...` lines to use the absolute path from the global storage (e.g., `Context: @${path.join(globalStoragePath, '.agent/skills', persona, 'SKILL.md')}`) so the agent reads the globally installed files instead of local ones.
   - `package.json` / `.vscodeignore`: Ensure `.agent` is included in the `.vsix` bundle.

## Addendum — SOTA Agentic Workflows & Trinity Routing Strategy
*Triggered by client request, Phase RESEARCH*

**Finding:** The client requested extended research on State-of-the-Art (SOTA) agentic workflows to maximize communication and cooperative results, along with precise routing rules defining when the HR agent (Trinity) should operate.

### 1. SOTA Agentic Workflow & Communication Models
Research into leading multi-agent frameworks (e.g., MetaGPT, AutoGen, ChatDev) reveals the following SOTA patterns for maximizing inter-agent cooperation:
- **Blackboard Architecture (Shared Context):** Agents communicate via a central, append-only message bus (like Devio's `inbox.jsonl`), ensuring all specialists share a single source of truth without tight point-to-point coupling.
- **Hierarchical Supervisor Routing:** A central Coordinator routes tasks to specialists based on their roles. Unstructured chat is minimized; all communication follows strict phase-based state machines.
- **Reflection & Critic Loops:** Incorporating an independent "Critic" or "HR" agent that observes the workflow and provides actionable feedback on process adherence, ensuring continuous improvement.
- **Standardized Operating Procedures (SOPs):** Agents perform best when given explicit, structured step-by-step instructions (skills) rather than open-ended prompts.

**Adaptation for Devio:** Devio already utilizes a Blackboard (`inbox.jsonl`) and Hierarchical Routing (via Coordinator). To achieve SOTA cooperative results, Devio must implement the **Reflection & Critic Loop** by formally integrating Trinity into the orchestration cycle.

### 2. Defining Trinity's Routing & Operating Triggers
Trinity's role is performance analytics and process improvement. To prevent Trinity from bottlenecking the critical development path, her routing must be precisely defined. Trinity should operate under the following triggers:

- **Trigger 1: Post-Mortem Analysis (End of Cycle):** 
  When the agency phase transitions to `DONE`, the Coordinator routes a task to Trinity to analyze the completed cycle. Trinity reads the recent `inbox.jsonl` entries to calculate metrics (e.g., number of revisions, QA rejection rates) and updates the Company and Agent Insight documents.
- **Trigger 2: Escalation / Deadlock Intervention:** 
  If the Coordinator detects excessive friction (e.g., a specific deliverable receives more than 3 consecutive `REQUEST_CHANGE` messages), the Coordinator temporarily halts the phase and summons Trinity. Trinity diagnoses the communication breakdown, outputs actionable feedback directly to the struggling agents, and updates their performance records.
- **Trigger 3: Periodic Background Audit:** 
  In a continuous operation mode, Trinity can run asynchronously (e.g., every 50 messages) to identify protocol violations (like unauthorized file edits) and flag them in the Agent Insights file for immediate correction by the Coordinator.

**Next Steps for Proposal:**
- Update the workflow routing rules in the proposal to explicitly include the three operating triggers for Trinity.
- Detail how the Coordinator will handle the "Escalation" trigger and route to Trinity during deadlocks.
- Emphasize how the inclusion of Trinity fulfills the SOTA Reflection & Critic Loop requirement to maximize agency cooperation.

## Addendum — Message Bus Protocol Updates (REQUEST_RESEARCH & CHALLENGE_SPEC)
*Triggered by client request, Phase DEVELOPMENT*

**Finding:** The client explicitly requested the addition of `REQUEST_RESEARCH` and `CHALLENGE_SPEC` message types to support the Lead Developer's workflow.

### Protocol Definitions for new Message Types:

**`REQUEST_RESEARCH`**
- **Sender:** Lead Developer (`agency-lead-developer`) or any agent needing deep-dive research.
- **Purpose:** Proactively requests a targeted research deep-dive on specific functional components (e.g., UI design) before architecture finalization or development.
- **Routing Rule:** Routed to `agency-researcher`.
- **Status on creation:** `OPEN`
- **Resolves when:** The Researcher posts an `INFO` message with findings, with `in_reply_to` referencing this message's ID.

- **Sender:** Lead Developer (`agency-lead-developer`) or Developer (`agency-developer`).

- **Routing Rule:** Routed to `agency-architect`.
- **Status on creation:** `OPEN`
- **Resolves when:** The Architect posts a `REVISION` updating the spec, and the challenger subsequently posts `APPROVE`.
